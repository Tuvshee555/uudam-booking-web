# Travel management QA and fixes — 2026-11-04

Hands-on test of the admin trip editor, the public website and the on-site
chatbot, done as a staff member would (real browser, real clicks, real saves),
against a disposable local copy of the live catalogue. Everything marked PASS
below was exercised in Chromium through Playwright and verified in the
database; nothing is marked PASS from reading code alone.

## 1. Safety: what was and was not touched

- **No production data was changed.** The live Neon database was read once,
  read-only, to copy the catalogue (61 trips, 540 departures, 475 itinerary
  days, categories, tags, site settings, the chatbot's `travel_trip_entries`
  table) into a local Postgres 16 database on this machine. Customers'
  bookings, enquiries, payments and the staff account were **not** copied;
  two local test logins were created instead (`admin@uudam.mn` as ADMIN,
  `staff-b@test.local` as STAFF, both local-only).
- Every edit below was made to that local copy. The app ran from this branch
  (`claude/optimistic-maxwell-j5w7em`), in `next dev` for the interactive
  tests and in a production build (`next build` + `next start`) for the
  page-cache check.
- Production is deployed from commit `f94fd1d`, which is the same code this
  branch started from, so the behaviour tested is the behaviour staff see.

## 2. The data flow, as it actually is

```
Admin editor (TripForm.tsx)
   └─ PUT /api/trips/[id]  ──►  Trip / Departure / ItineraryDay tables (Neon, Postgres)
          │                            │
          │  queueTripSync + deliver   ├──► public pages (cached a day, refreshed by the save: server/revalidate.ts)
          │  (HTTP, shared secret)     ├──► /api/trips, /api/trips/[slug]/availability (live reads)
          ▼                            └──► on-site chatbot /api/ai/chat  (reads Trip + Departure directly)
Messenger chatbot project (Uudam-Chatbot, separate code, SAME database)
   └─ canonical table travel_trip_entries  ──► its answers
   └─ "projection" writes back into Trip / Departure (lastSyncedAt == updatedAt on every synced trip)
```

Two chatbots exist, and they read trip facts from different places:

| Chatbot | Where its facts come from | Changed by this work |
| --- | --- | --- |
| On-site "Аяллын зөвлөх" widget (this repo, `/api/ai/chat`) | `Trip` + `Departure` rows, same as the pages | Yes — see fix 6 |
| Messenger chatbot (repo `Tuvshee555/Uudam-Chatbot`) | Its own `travel_trip_entries` row (prices, fare table), plus live `Departure` rows for seats/status | No code access from this session; website → chatbot delivery verified and documented |

The Messenger chatbot receives every website save through
`POST /api/internal/website-trip` (its `websiteTripBridge.ts`) and merges it
per date; it then writes the result back into the website's `Trip` row within
about two seconds (`lastSyncedAt` equals `updatedAt` on every recently synced
trip in the live database). Its bridge refuses a fare edit while an older
disagreement on that trip is open (`ignored: price_groups, reason:
open_conflict`), which is exactly what the live sync report on
"ХАЙНАН – ХӨХ ХОТООС САНЬЯА НИСЛЭГТЭЙ 2" shows for 2026-11-03. The website
already surfaces this in the editor ("Сүүлийн засварын зарим талбарыг chatbot
аваагүй" with a "Зөрүүг шийдэх" button); staff have to settle the listed
disagreement on the "Chatbot-той харьцуулах" tab for the next fare save to go
through.

## 5. Observations in the live data (read-only, not changed)

- "ХАЙНАН – ХӨХ ХОТООС САНЬЯА НИСЛЭГТЭЙ - 1": website `price` 3,090,000 but the chatbot's canonical `adult_price` is 3,033,000. The chatbot answers prices from its per-date fare table, so customers may still hear the right per-date amount, but the two base figures disagree. Worth checking in the chatbot admin.
- On 2026-11-03 the chatbot refused the website's fare edit on "…НИСЛЭГТЭЙ 2" (`open_conflict`) and recorded conflicts on "hainan". This is the most likely source of "the chatbot and the website don't match": the website saved, the chatbot kept its own values. The editor's "Chatbot-той харьцуулах" tab is where those are settled.
- Several trips carry phantom cancelled dates in 2027/2028 (e.g. 2027-09-15, 2028-09-22 on "hainan") created by an earlier import that read "9 сарын 15" into several years. They are harmless and, after fix 1, no longer clutter the editor.
